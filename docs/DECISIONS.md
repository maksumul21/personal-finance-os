| D-001 | 2026-11-02 | Light double-entry ledger (`Transaction` + `LedgerEntry`) instead of a flat transaction table. | Transfers, credit cards, loans, cross-currency and net worth stay correct by construction. |
| D-002 | 2026-11-02 | Loan principal repayment = TRANSFER to the loan's liability account; only interest is an EXPENSE. "Loan Payments" category stays for untracked loans. | Principal reduces a liability; it is not consumption. |
| D-003 | 2026-11-02 | Credit-card debt appears in the Debt module through its linked credit-card account, never as a second record. | Prevents double counting. |
| D-004 | 2026-11-02 | Multi-tenant (open signup). | Default from plan. |

| D-007 | 2026-11-02 | Refunds recorded as EXPENSE with `isRefund = true`; they reduce category spending. | Keeps refunds in the right category. |
| D-008 | 2026-11-02 | Local development and integration tests use `prisma dev` (embedded Postgres) because Docker is not installed. Production uses Supabase Postgres. | No Docker on the dev machine. |
| D-009 | 2026-11-02 | Dev-only auth bypass: when `NODE_ENV=development` and `DEV_AUTH_EMAIL` is set, requests act as that local user. Ignored, with an error logged, in any other environment. | Lets the app run locally before Supabase credentials exist. Never active in production builds. |
| D-010 | 2026-11-02 | Prisma 7.10.1 (stable) instead of the npm `latest` tag, which currently points to an 8.0 release candidate. | Stability. |
| D-011 | 2026-11-02 | Opening balance is a field on Account, not a transaction; it never counts as income. | Matches PRD §7.3 formula. |
| D-012 | 2026-11-02 | Transactions are hard-deleted (entries cascade) and recorded in `AuditLog`. Accounts and categories are archived. | Soft-deleted rows that a query forgets to filter cause wrong totals. |
| D-013 | 2026-11-02 | Account types: CASH, BANK, SAVINGS, MFS, CREDIT_CARD, LOAN, INVESTMENT, OTHER_ASSET. Nature (ASSET/LIABILITY) derived from type. bKash/Nagad/Rocket are MFS presets via `provider`. | PRD §7.1 + debt/investment design. |
| D-014 | 2026-11-02 | Category hierarchy limited to 2 levels (group → subcategory). | Matches PRD default categories; keeps budgeting roll-ups simple. |
| D-015 | 2026-11-02 | `cacheComponents` disabled (the Next 16.4 template enables it). | Every page renders per-user financial data on request; nothing is shareable across users to cache. Route `loading.tsx` files give instant navigation feedback. Revisit if static marketing pages are added. |
| D-016 | 2026-11-02 | Dismissed insights are remembered per browser (localStorage), per period. | Per-viewer convenience; critical insights can't be dismissed. Moves to the database if cross-device dismissal is needed. |
| D-017 | 2026-11-02 | A budget can't limit both a category group and one of its subcategories. | A group's limit already includes its subcategories; both would double-count spending. |
| D-018 | 2026-11-02 | Budget comparisons for a running period use the same elapsed days of the previous period (1–10 Nov vs 1–10 Oct). | Comparing a partial month with a full one is misleading (PRD §15.4). |
| D-019 | 2026-11-02 | Rollover carries only unused budget by default; overspending is not carried forward. | One bad month shouldn't silently shrink the next. |
| D-020 | 2026-11-02 | Chart colours use the validated categorical palette (dataviz skill); status colours (warning/serious/overspent) are separate tokens and always come with an icon and label. | Colour-blind safety and never colour-only meaning. |
| D-021 | 2026-11-02 | The shared `Select` ignores Radix's empty `onValueChange("")`. | Radix emits it on mount; it caused a navigation loop in URL-driven filters and could clear form selections. |
| D-022 | 2026-11-02 | Until investment holdings are valued at market (Phase 4), an INVESTMENT account counts in net worth at its ledger balance (money put in). It stays out of Total Balance. Net worth = Σ signed balances of active accounts; the trend uses the same rule. | Previously investment accounts counted as zero, so moving money into one made net worth drop by that amount. |
| D-023 | 2026-11-02 | A bill can be paid only from an account in the same currency as its payment account. | The bill amount is in that currency; paying from another would post the number unconverted. |
| D-024 | 2026-11-02 | Post-login redirects go through `safeRedirectPath()` (WHATWG URL parsing against a probe origin). `NODE_ENV` defaults to `production`. | Closes the `/\evil.com` open redirect; a missing `NODE_ENV` can never enable the dev auth bypass (D-009). |
| D-025 | 2026-11-02 | Changing a category between income and expense is refused while it or any subcategory is used by a transaction, recurring rule or bill. | The kind change cascades to subcategories and would leave transactions on a category of the wrong type. |
| D-026 | 2026-11-02 | Loans: `LoanTerms` (1:1 with a LOAN account) holds the contract; the amount owed is always the account's ledger balance. Each `LoanPayment` links its principal TRANSFER and interest EXPENSE (source `DEBT`); both are created and deleted together and can't be edited individually. Interest is the lender's figure when entered, otherwise one month's interest on the outstanding balance. A payment above what's owed is refused, never trimmed. Pay from an active asset account in the loan's currency. | Keeps D-002 exact and the two halves of an EMI in sync. |
| D-027 | 2026-11-02 | Loan foreign keys cascade at the database level (so deleting a user works); the services refuse to delete an account or category a loan uses, or change a loan account's type or currency while it has terms. Removing loan terms keeps posted transactions as ordinary ones. | Same approach as recurring rules and bills. |
| D-029 | 2026-11-02 | Investments (supersedes D-022): holdings belong to an INVESTMENT account; buys and sells are `HoldingTrade`s using average cost; prices are recorded by the user and valuation uses the latest on or before the date (unpriced = at cost, flagged). Trades never create ledger entries, and gains are never income or expenses. Account value = ledger balance + realised + unrealised gains; net worth (KPI and month-end trend) uses it. A buy must be covered by the account's uninvested cash on its date, so money is transferred in first. | Keeps spending and income honest while net worth reflects market value. |
| D-030 | 2026-11-02 | Net worth = active accounts (investments at market value) + manual assets − manual liabilities. Manual items (property, vehicles, gold, money lent/borrowed, tax due) hold dated valuations; the value on a date is the latest on or before it (zero before the first; 0 = sold/settled). Kind and currency are fixed once created; archived items drop out, like accounts. One shared module (`net-worth.query.ts`) feeds the dashboard KPI, the dashboard trend and the Net Worth page. | Matches the ARCHITECTURE.md formula and keeps every net worth figure consistent. |
| D-031 | 2026-11-02 | The financial calendar is a read-only view assembled on request: stored bill occurrences plus projections past the 90-day horizon, unposted recurring occurrences, recorded EMI payments plus remaining due dates up to payoff (anchored to the first payment date), active goal target dates, and recorded daily income/spending. No new tables. "Still to pay/expected" counts open base-currency items only; EMIs count in full (cash leaving). | Nothing to keep in sync; every source stays the single source of truth. |
| D-032 | 2026-11-03 | Safe-to-spend (formula approved by the product owner): balances of active asset accounts marked "include in safe-to-spend" (never investment accounts) − unpaid bills paid from those accounts, scheduled expenses from them, scheduled transfers out of them to non-included accounts, and EMIs paid from them, due up to the window end (overdue included) − what active goals still need this month (required monthly − net deposits this month). Window: today to the day before the next scheduled income; month-end when none is scheduled. Per-day = safe ÷ days left, rounded down. Card-paid bills count when the card is paid. Foreign items without a rate are left out and counted. | Agreed formula; the boundaries keep it conservative and avoid double counting. |
| D-033 | 2026-11-03 | Cash-flow forecast: projects the cash pool (active asset accounts other than investments, matching Total balance) day by day for 30/90/180 days. Flows come from one shared module (`scheduled-flows.ts`, also used by safe-to-spend): recurring income/expenses on pool accounts, recurring transfers crossing the pool's edge, unpaid bills paid from the pool (projected past the stored horizon), EMIs paid from the pool; overdue items land on today; card-paid bills excluded. Optional day-to-day spending (on by default, clearly labelled) = average of unscheduled expenses (source MANUAL/IMPORT, refunds netted) over the last 90 days or the history available, applied from tomorrow. Unscheduled income is not assumed. Reached from the Calendar page and the Safe-to-spend breakdown (the PRD §3 navigation has no forecast item). | Transparent, conservative estimate built only from the user's records; one flow builder keeps safe-to-spend and the forecast consistent. |
| D-034 | 2026-11-03 | Reports v1 (PRD §14 detail beyond §14.2 unknown): period presets or a custom range (≤ 5 years); a running period is reported to today and compared with the same elapsed days of the previous period (D-018). Summary (income, expenses, net, savings rate, expense-to-income §14.2, average daily spend), spending and income by category with subcategory drill-down, share and change, month-by-month table, 10 largest expenses, money in/out per account (transfers included, labelled as movement). CSV download via `/reports/export` (signed-in only, `no-store`, UTF-8 BOM, cells starting with = + - @ neutralised against formula injection). | Useful, accurate reports from existing data; safe export. |
